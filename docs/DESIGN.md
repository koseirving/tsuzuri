# つづり（tsuzuri）— 設計書 v0.1

**仮称・仮説段階。需要、継続率、収益性は未検証。**
整理日: 2026-09-30。Product ID: `tsuzuri`。この文書は設計の合意用であり、バックログの代わりではない。

> 好きになるのは、その人の毎日。

---

## 1. 何をつくるか

プロフィールの自己紹介ではなく、**日々の小さな出来事を書いた日記から人柄を知り、友達になり、双方が望めばその先に恋愛もある**出会いのアプリ。
同性・異性どちらの出会いにも対応する。

### 1.1 検証したい価値（仮説）

- 写真と条件で選ぶ既存のマッチングアプリに疲れた人は、「文章から相手を知る」出会いに乗り換えるか。
- 「いいね」ではなく**一文への感想**から始まる会話は、最初の返信率と会話の続き方を改善するか。
- 急かさない仕組み（既読なし・人数制限・連続記録なし）でも、書く・読む習慣が続くか。

### 1.2 想定する利用者

- 成人（18歳以上。公開版では年齢確認必須）。
- 写真の第一印象や「スワイプ」による選別に疲れている人。
- 文章を書くこと・読むことが苦にならない人。長文は必須にしない。
- 恋愛を急がず、まず友人関係から始めたい人。同性の友人探しだけに使ってもよい。

## 2. 大切にすること → 仕組み

| 大切にすること | 仕組み | やらないこと |
|---|---|---|
| 返信を急かさない | 既読表示なし、返信期限なし、「未返信」バッジなし | オンライン表示、最終ログイン表示 |
| 人気を競わない | 公開いいね数・フォロワー数・ランキングなし | 「人気の日記」「注目の人」 |
| 一人ずつ向き合う | 紹介は1日3人、送れる感想は同時に3通まで、つながりは同時に3人まで | 無制限スワイプ、一斉送信 |
| 無理なく続ける | 連続投稿の報酬・休んだ罰なし。お休みモードあり | ストリーク、ログインボーナス |
| 安心して離れられる | 理由なしの見送り・関係終了・ブロック。相手に理由は通知しない | 「断られました」通知 |
| 人を点数にしない | 日記から性格を断定するAIスコアは使わない | 相性％、性格タイプ判定 |

「まめさ」は投稿回数で採点しない。相手の日常に関心を持ち、無理のないペースで関わることとして扱う。

## 3. 出会いの流れ

```text
① 書く        日常を少し書く（1行でもよい。毎日の義務はない）
   ↓
② 読む        1日3人の日記が届く。顔写真はまだ見えない。気になった人の過去の日記も読める
   ↓
③ 感想を送る   心に残った一文を選んで感想を書く（「いいね」だけは無い）
   ↓
④ つながる     受け取った人が「話したい」と返すと、ふたりがつながる
   ↓                     （つながることは交際への同意ではない、と明示）
⑤ ふたりの日記  日記に返事を添え合いながら、ゆっくり親しくなる
   ↓
⑥ 写真を同時公開（任意）  双方が同意したときだけ、同じ瞬間に公開
   ↓
   友達のまま続けても、双方が望めば恋愛に進んでもよい
```

### 3.1 感想（最初の一通）

- 相手の日記から**一文を選んで引用**し、それに対する感想を書く（10〜400字）。
- 同時に「返事待ち」にできる感想は最大3通。返事がなくても催促はできない。
- 受け取った側の選択肢は「話したい」「見送る」の2つだけ。
  - 見送っても送った側には通知しない。送った側の一覧では14日後に「そっと閉じました」として静かに片づく（誰の意思かは表示しない）。
- 送る前に、外部連絡先（電話番号・メールアドレス・URL・SNS ID らしき文字列）が含まれていないか確認する。含まれる場合は「つながる前の連絡先交換は控えてください」と表示し、送信できない。

### 3.2 つながり

- 同時に続けられるつながりは最大3人。上限に達している間は、新しい紹介を減らし「今のつながりを大切にする期間」として表示する。
- つながると、ペンネーム・年代・地域（都道府県）・自己紹介文が互いに見える。写真はまだ見えない。
- つながった直後に「つながることは、交際への同意ではありません。いつでも理由なしで関係を終えられます」と一度だけ表示する。

### 3.3 ふたりの日記

- ふたりだけに見える日記帳。どちらも自由に書き足せ、各日記に「返事」を添えられる。
- 既読表示なし、入力中表示なし、通知は「ふたりの日記に新しいページがあります」の1種類で、1日1回までにまとめる（設定で切替）。

### 3.4 写真の同時公開

- どちらかが「写真を見せ合いませんか」と提案する。提案前に以下を必ず表示する:
  - 相手も同意した時点で、**双方の写真が同時に**公開される。
  - 公開後に取り消しても、相手がすでに見た事実は消せない。
  - 同意しないことは失礼ではない。理由を伝える必要はない。
- 状態: `hidden → proposed(提案者) → revealed`。相手が同意する前なら提案者は取り消せる。
- 相手は「同意して公開」「今はまだ」を選べる。「今はまだ」は提案者に通知しない（提案は保留のまま残り、30日で自然に消える）。
- 写真は公開プロフィールには置かない。サーバー側で `revealed` のつながりのメンバーにだけ、短時間有効な署名付きURLを発行する。

### 3.5 離れる

- どの段階でも「関係を終える」「ブロック」「通報」ができる。
- 関係を終える: ふたりの日記は双方から読めなくなる（運営は通報対応のため90日保持。期間は要法務確認）。相手には「この関係は終わりました」とだけ表示する。以後、相互に紹介されない。
- ブロック: 相手から自分の日記・プロフィールが見えなくなり、紹介もされない。相手には通知しない。
- 通報: 種別（なりすまし・勧誘や営業・性的な内容・脅しや嫌がらせ・未成年の疑い・その他）＋任意の説明。通報すると自動でブロックもされる。

## 4. 同性・異性の出会いの扱い

- 自分について: 性別（女性／男性／ノンバイナリー／回答しない）。
- 出会いたい相手（複数選択）: 女性／男性／ノンバイナリー。
- 紹介は**双方向の一致**だけ: A の出会いたい相手に B の性別が含まれ、かつ B の出会いたい相手に A の性別が含まれるとき。
  - 「回答しない」の人は、出会いたい相手に「すべて」を選んだ人とだけ一致する。
- 性別・性的指向は他のユーザーに表示しない（プロフィールに出すかは本人が選ぶ。既定は非表示）。
- 性的指向そのものは入力させない。必要なのは「誰と出会いたいか」だけ。

## 5. 画面

下部タブは **読む・書く・ふたり** の3つ。設定は右上から開く。

| # | 画面 | 主な内容 |
|---|---|---|
| 0 | はじめに | 成人確認 → ペンネーム・年代・地域 → 自分の性別・出会いたい相手 → 最初の日記（1行でよい） → 大切にすること の説明 |
| 1 | 読む | 今日の3人（ペンネーム・年代・地域・日記の冒頭）。明日また届く、と表示。無限スクロールなし |
| 1a | 日記を読む | その人の公開日記（新しい順）。文をタップして選ぶ → 感想を書く |
| 1b | 感想を書く | 選んだ一文の引用＋感想入力。外部連絡先チェック。送信後は「届けました。返事はゆっくり待ちましょう」 |
| 2 | 書く | 今日の問いかけ（任意）・本文・公開範囲（紹介に使う／つながった人だけ／自分だけ）。過去の自分の日記一覧 |
| 3 | ふたり | 届いた感想・送った感想・つながり（最大3） |
| 3a | 届いた感想 | 引用＋感想＋送り主の日記へのリンク。「話したい」「見送る」 |
| 3b | ふたりの日記 | ふたりのページと返事。写真の同時公開、関係を終える・ブロック・通報 |
| 3c | 写真を見せ合う | 同意事項の説明 → 提案／同意 → 同時公開 |
| 4 | 設定 | プロフィール、出会いたい相手、お休みモード（紹介を止める）、通知、ブロック一覧、データの書き出し、退会 |

### 5.1 見た目

- 文章が主役。本文 17px 前後、行間 1.8、1行 34〜38字程度の余白。
- 紙と墨のような落ち着いた色（生成り・墨・くすんだ藍と金木犀色を差し色に）。
- 数値（件数・%）をできるだけ出さない。バッジは「新しいページ」の点のみ。

## 6. データ設計

アプリ内部は `TsuzuriBackend` インターフェースに依存し、実装を差し替える。

- `DemoBackend`: 端末内だけで動く試作用。架空の書き手を同梱し、app_core の `LocalStore` に保存。
- `FirebaseBackend`（未実装）: 製品専用の Firebase プロジェクト（`tsuzuri-dev` / `tsuzuri-prod`）を分けて作る。**アカウント作成・契約は別途承認が必要**。

### 6.1 型（アプリ内のモデル）

```text
Profile        id, penName, ageBand(20代前半…), prefecture, bio, gender, seeking{…}, photoRef?, paused
DiaryEntry     id, authorId, body, prompt?, visibility(intro|connections|private), createdAt
Letter         id, fromId, toId, diaryId, quote, body, status(pending|accepted|declined|closed), createdAt
Connection     id, members[2], createdAt, status(active|ended), photo{state, proposedBy?, revealedAt?}
SharedPage     id, connectionId, authorId, body, createdAt, replies[ {authorId, body, createdAt} ]
Block          blockerId, blockedId, createdAt
Report         id, reporterId, targetId, context(letter|page|diary|profile), category, note, createdAt
DailyIntro     userId, date(YYYY-MM-DD, JST), candidateIds[≤3]
```

### 6.2 Firestore（本番案）

```text
users/{uid}                    本人のみ読み書き: 性別、出会いたい相手、年齢確認状態、通知設定
profiles/{uid}                 紹介・つながりの相手が読める範囲だけ: penName, ageBand, prefecture, bio
diaries/{id}                   authorId, body, visibility, createdAt   ※ intro は紹介された人のみ読める
letters/{id}                   fromId, toId, quote, body, status ※ 送り主・宛先のみ
connections/{id}               members, status, photo ※ メンバーのみ
connections/{id}/pages/{pid}   ふたりの日記 ※ メンバーのみ、status=active の間
intros/{uid}/days/{date}       candidateIds ※ Cloud Functions のみ書き込み
blocks/{uid}/targets/{tid}     本人のみ
reports/{id}                   作成のみ許可、読み取りは運営
```

- 紹介の選定・感想の上限・つながり上限・写真公開の状態遷移は、**クライアントではなく Cloud Functions で検証**する（ルールだけで不正に上限を超えられないように）。
- 写真は Cloud Storage の非公開パス `photos/{uid}/…`。読み取りは関数が発行する署名付きURLのみ。

### 6.3 紹介の選び方（1日1回、日本時間 5:00）

1. 双方向の性別一致。
2. どちらかがブロック・通報・関係終了した相手、お休み中の人、つながり上限の人を除外。
3. 直近30日に「紹介に使う」日記が1件以上ある人。
4. 過去30日に紹介済みの人を除外。
5. 残りから無作為に3人（利用者と日付ごとに固定。v1 で「最近書いた人を少し優先」を検討）。**文章内容からの性格スコアや相性％は使わない。**

### 6.4 サーバー実装（v1 の土台・未デプロイ）

`functions/`（Cloud Functions, TypeScript）と `firestore.rules` / `storage.rules` / `firestore.indexes.json`。

- **クライアントは直接書き込まない。** 書き込みはすべて関数経由で、上限・双方向の一致・写真の同意・ブロックを関数が検証する。
- **読める範囲**
  - 他人のプロフィールと日記は「紹介された（2日間）」「感想をやりとり中（14日間）」「つながっている」のどれかに当てはまり、かつブロック関係にないときだけ読める。
  - この閲覧権限は関数が `access/{viewer}_{author}` に付与する。
  - 他人の日記の一覧は `readDiaries` 関数が返す。コレクションを直接一覧できないようにするため。
- **感想**
  - 紹介された人にだけ送れる。1方向につき1通まで（`letters/{from}_{to}`）。
  - 見送りも期限切れも、送り主から見ると同じ「閉じた」状態（`closed`）になる。
- **つながりと写真**
  - つながりは1組につき1つまで（`connections/{小さいuid}_{大きいuid}`）。終わったつながりは作り直せない。
  - 写真は `photos/{uid}/profile.jpg` に置き、直接は読めない。公開後に `revealedPhotoUrl` 関数が5分だけ有効な署名付きURLを出す。
- **定時処理**
  - 毎日5:00（日本時間）に紹介を作る。
  - 1時間ごとに、14日たった感想と30日たった写真の提案を静かに閉じる。
- **年齢確認**：`REQUIRE_AGE_VERIFICATION`（既定 true）のあいだ、未確認の人は感想・つながり・紹介の対象外。
- **検証**
  - `npm test`（25件）：この環境で実行済み。
  - `tsc` とルールのエミュレータテスト：CI（`.github/workflows/ci.yml`）で実行する。

**未決事項（サーバー）**
- App Check を必須にしている。アプリ側で App Check を入れるまで、関数は呼べない。
- 公開後に写真を差し替えられる。差し替えたら再同意を求めるか、要検討。
- 写真の内容チェック（不適切な画像）の方法は未定。
- 署名付きURLの発行には、実行サービスアカウントに Token Creator 権限が必要。
- 紹介の計算は利用者ごとにクエリを数回投げる。数千人規模で見直す。

## 9. 検証案

試作 v0 で 5〜8人に触ってもらい、次を観察する（数値目標は観察後に決める。今は仮置きしない）。

- 日記を読んで「感想を書きたい」と思える一文が見つかるか。見つからない場合、何が足りないか。
- 一文を選んで感想を書く操作が、「いいね」より負担に感じないか。
- 写真を見ないまま「話したい」を押せるか。不安は何か。
- 写真の同時公開の説明で、何が起こるか正しく理解できるか（理解度を口頭で確認）。
- 既読なし・人数制限を「物足りない」と感じるか「安心」と感じるか。

v1 で計測するイベント案（app_core の閉じた列挙に追加する別タスクが必要）:
`diary_written`, `intro_opened`, `letter_sent`, `letter_accepted`, `connection_started`, `page_written`, `photo_revealed`, `connection_ended`, `report_sent`。
本文・ペンネームなど自由入力の文字列はイベントに含めない。
